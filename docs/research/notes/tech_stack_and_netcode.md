## 1. Netcode: how Clash Royale-style real-time PvP works, and lockstep vs server-authoritative vs rollback

### Takeaway
Supercell has never published a talk or post on Clash Royale's netcode (none found). The available evidence comes from Supercell's own support page, reverse-engineering projects and outside analysis. It points to this design: one deterministic game-logic layer compiled into both client and server; players send only "play card X at (x,y)" commands; the server owns the match clock and keeps simulating even when a player drops. For dozens of units and only two players, the cheapest robust pattern for a tiny team is "server-scheduled deterministic command relay": every command is stamped to run a few ticks in the future (input delay), which hides latency, and the server optionally re-runs the same sim for validation. Rollback is unnecessary for this genre, and full state-sync is bandwidth-heavy with 50–100 units.

### Cited Findings
**Clash Royale specifics (no official netcode documentation exists)**
- Supercell's official support article says that during a connection problem in Clash Royale you cannot deploy cards, but "the battle will continue and your opponent can still deploy cards". So the match keeps running server-side without the disconnected player. The same article says Brawl Stars instead replaces a disconnected player with a bot. — [Supercell Support: Unstable Connection](https://support.clashroyale.com/hc/pl/articles/49484886660251-Unstable-Connection)
- A reverse-engineering/private-server project (Scroll) reports that "Supercell's games have their game logic implementation included in both client and server, for independent execution", so a full server emulator has to rewrite that logic. This is a third-party claim. — [Supercell/Scroll (git.xeondev.com)](https://git.xeondev.com/Supercell/Scroll)
- An analysis of a leaked v1 Clash Royale client describes its Logic subsystem as "a deterministic simulation engine", with player inputs handled as command objects so that client and server stay in sync. This describes an old client, not confirmed current production netcode. — [DeepWiki: Clash-Royale-v1-Client-Leak](https://deepwiki.com/clashRoyaleClients/Clash-Royale-v1-Client-Leak)
- An outside developer's 2016 analysis (labeled by the author as a guess) proposed "a client/server architecture where both the server and the client simulate the game synchronously", with the server validating actions. — [Gemserk blog, 2016](https://blog.gemserk.com/2016/09/05/analyzing-clash-royale-multiplayer-solution/)
- A fan web port targeting the April 2019 build 2.7.4 implements the battle as a standalone, tick-based simulation at 20 Hz (`step(battle, commands)` returns events). This is the port's own design and may not match Supercell's tick rate. — [Clash-Royale-Web-Port (GitHub)](https://github.com/Guernica4u/Clash-Royale-Web-Port)
- A tick-rate database lists Clash Royale at about 10 Hz and labels the figure an estimate, because Supercell publishes no tick rate. — [PingPacketTest](https://pingpackettest.com/supported-games)
- Several research and hobby projects have rebuilt CR's battle logic as integer-exact, deterministic simulators: Hasty-CR ("integer-exact physics from client data, 1,600+ tests") and a C++ deterministic simulator with Python bindings. This shows the battle model can be reproduced with integer math. — [Hasty-CR](https://github.com/hastylmao/Hasty-CR); [clash-royale-env](https://github.com/cole-zoom/clash-royale-env)
- Supercell's GDC talks on Clash Royale (Stefan Engblom, GDC 2017) and Brawl Stars (2019) are about card balance, design and progression, not networking. — [GDC 2017 vault](https://www.gdcvault.com/play/1024272/); [GDC news, Brawl Stars 2019](https://gdconf.com/news/go-inside-design-supercells-new-hit-game-brawl-stars-gdc-2019)
- Supercell's published server-side engineering covers backend infrastructure: real-time event streaming (ScyllaDB Summit 2024), and account tokens signed by an account API and presented to the game server. — [ScyllaDB tech talk: Real-time persisted events at Supercell](https://www.scylladb.com/tech-talk/real-time-persisted-events-at-supercell/)

**Lockstep, input delay, rollback**
- A community proposal for client-server lockstep: the client sends commands stamped for step X+N, where N comes from the round-trip latency. One developer reported about 200 ms from issuing a command to its execution in their lockstep implementation. A server can also declare a step complete for a slow client and schedule that client's late commands into an upcoming step. — [GameDev.net: Lockstep Protocol – Reducing Latency](https://gamedev.net/forums/topic/708508-lockstep-protocol-for-multiplayer-reducing-latency/); [GameDev.net: Client-server RTS lockstep](https://gamedev.net/forums/topic/644053-client-server-rts-lockstep/)
- Rule of thumb from a deterministic-netcode guide: input delay of about half the median round-trip time. Less delay than that causes constant mispredictions under rollback. The same guide says RTS games historically favored lockstep because syncing state for hundreds of units is hard. — [yal.cc: Preparing your game for deterministic netcode](https://yal.cc/preparing-your-game-for-deterministic-netcode/)
- A common middle ground is a small input delay plus rollback for the remaining latency. — [Meseta: Netcode concepts part 3](https://meseta.medium.com/netcode-concepts-part-3-lockstep-and-rollback-f70e9297271); vendor overview at [Edgegap: Input delay vs rollback](https://edgegap.com/blog/how-to-mitigate-latency-in-multiplayer-games-input-delay-vs-rollback)
- Photon Quantum is a deterministic predict/rollback engine: clients roll back to the latest verified frame and re-simulate. Its docs say re-simulating many expensive entities "can become significant" and offer "prediction culling" (predict only near the local player) as the mitigation. Culled entities can jitter if they share an RNG session. — [Photon Quantum 3 docs: Prediction culling](https://doc.photonengine.com/quantum/v3/manual/prediction-culling); [Quantum 3: Mispredictions and entity views](https://doc.photonengine.com/quantum/current/concepts-and-patterns/mispredictions-and-entity-views)
- Glenn Fiedler (Gaffer on Games) describes peer-to-peer lockstep and notes that "it's exceptionally difficult to ensure that a game is completely deterministic". He contrasts it with client/server and client-side prediction. — [Gaffer on Games: What Every Programmer Needs To Know About Game Networking](https://gafferongames.com/post/what_every_programmer_needs_to_know_about_game_networking/)

**Determinism pitfalls (devices, JavaScript)**
- Gaffer on Games: getting exactly the same floating-point results on different machines is "very difficult". It is possible with the same compiler and architecture plus platform tricks, usually at lower float performance. — [Gaffer on Games: Floating Point Determinism](https://gafferongames.com/post/floating_point_determinism)
- GDC 2024 (Frontier, *Warhammer Age of Sigmar: Realms of Ruin*, an RTS): floating point "can be used… but requires extreme care", and the talk recommends taking the performance hit and using fixed-point. It lists three reasons for a deterministic sim: network sync, replays and anti-cheat. — [GDC 2024 slides: Pollard & Bradley, Cross-Platform Determinism](https://media.gdcvault.com/gdc2024/Slides/GDC+slide+presentations/Pollard_Bradley_CrossPlatformDeterminism+2024-03-26+09.34.19.pdf)
- A lockstep postmortem describes a team that banned floats from its simulation, switched to fixed-point math, and trapped stray float use with the floating-point inexact exception. — [Game Developer: Minimizing the pain of lockstep multiplayer](https://gamedeveloper.com/programming/minimizing-the-pain-of-lockstep-multiplayer)
- JavaScript: Rapier's JS docs warn that `Math.sin`/`Math.cos` are "not cross-platform deterministic". Fixes used in practice: a TypeScript fixed-point library with a hardcoded sine lookup table (so every peer computes identical results), and an fdlibm-based package that swaps `Math` transcendental functions for bit-identical browser and server output. No source gives a formal V8 vs JavaScriptCore vs SpiderMonkey comparison. — [Rapier JS determinism](https://rapier.rs/docs/user_guides/javascript/determinism); [DEV: Deterministic physics in TS – fixed-point engine](https://dev.to/shaisrc/deterministic-physics-in-ts-why-i-wrote-a-fixed-point-engine-4b0l); [@caputchin/determinism](https://www.pkgstats.com/pkg:@caputchin/determinism)
- Rune (a JS multiplayer platform) published an engineering post on making JS deterministic for its rollback netcode. — [Rune: Making JS deterministic for fun and glory](https://developers.rune.ai/blog/making-js-deterministic-for-fun-and-glory/)
- A Unity forum thread reports float determinism problems between Intel and AMD CPUs, and points to fixed-point libraries for stable replays. — [Unity Discussions: Floating point determinism Intel vs AMD](https://discussions.unity.com/t/floating-point-determinism-in-unity-intel-vs-amd/813566)

**SEA mobile latency**
- Singapore had the lowest median mobile latency in SEA (9 ms) in early 2021, and the Philippines 33.7 ms. These are access-network figures, not the path to a game server. — [Statista/Tutela: SEA median mobile latency](https://www.statista.com/statistics/1252705/sea-median-mobile-latency-by-country/)
- Indonesia Q3 2019: Telkomsel had the lowest latency of the operators measured, at 45.5 ms. — [Statista: Indonesia latency by provider](https://www-statista-com.ezproxy.canberra.edu.au/statistics/1100276/indonesia-latency-experience-by-provider)
- A 2026 Ookla-based report (via TechWire Asia) puts Singapore's multi-server latency at 24.6 ms. Under load, latency degrades 3.7x in Indonesia and 5.2x in the Philippines. I could not confirm the attribution of the summary to that article. — [TechWire Asia, July 2026](https://techwireasia.com/2026/07/ai-workloads-apac-mobile-networks/)
- OpenSignal (2018): very few 4G networks measured sub-30 ms latency, and Singapore's M1 and Singtel were two of them. — [OpenSignal 2018](https://opensignal.com/2018/12/12/singapores-secret-mobile-broadband-weapon-latency)

### Inferences
- **Recommended netcode for this game: server-scheduled deterministic command relay (lockstep-style, server as clock/referee).** Clients send only card-play commands of a few bytes. The server stamps each command with an execution tick (current tick + delay of roughly 150–300 ms) and broadcasts it to both clients. Both clients run the identical fixed-timestep deterministic sim, the server confirms ticks, and nobody rolls back. Bandwidth stays tiny no matter how many units are on screen, which suits 50–100 units on SEA mobile networks. The Supercell support statement (battle continues and the opponent can still deploy while you are disconnected) fits this model: the server keeps advancing ticks and simply receives no commands from the dropped player.
- **Latency hiding is mostly a design job.** A summoning/deploy animation of about 0.5–1 s, a placement "ghost" shown instantly on the local client, and the elixir being deducted locally make a 150–300 ms command delay invisible. The doubling of loaded latency in Indonesia and the Philippines (3.7–5.2x) argues for a generous fixed delay, possibly adaptive, rather than rollback.
- **Reconnection** comes naturally with deterministic command logs. On reconnect, the server sends the seed plus the full command list, or a periodic snapshot plus the commands after it, and the client fast-forwards the sim headlessly. Spectating and replays work the same way.
- **Server-authoritative simulation (server runs the sim and streams state)** is the simpler mental model and works without strict determinism. The cost is streaming positions and HP for up to 100 units: bandwidth, interpolation code and server CPU per match. A hybrid is viable: the server runs the same deterministic sim, the clients run it too, and the server sends periodic checksums or snapshots for desync recovery. That way, determinism bugs do not break matches during the prototype phase.
- **Rollback (Quantum-style)** buys snappier input, but for a card game with a built-in deploy delay the benefit is small. Re-simulating 50–100 units several times per frame on a low-end phone is a real CPU cost, as Photon's own docs acknowledge with prediction culling.
- **For a TypeScript stack:** keep all simulation math in integers or fixed-point (for example, positions in 1/1000 tiles), use a seeded integer PRNG, and replace trig/sqrt with lookup tables or integer approximations. Iterate entities in a stable order, never iterate a JS `Map`/`Set` whose order depends on insertion timing from networked events, and never use `Math.random`, `Date.now` or frame delta inside the sim. Keeping the sim pure TS lets the same code run in the browser, Node (Colyseus/Nakama TS runtime) and Cloudflare Workers.

### Gaps
- No primary Supercell source on Clash Royale's tick rate, input delay, or whether its server re-simulates or only relays. The 10 Hz and 20 Hz figures are estimates or fan reimplementations.
- I could not verify (search budget exhausted) the commonly cited Clash Royale "1 second deploy time" for most troops, which would be the main latency-hiding device. The report writer should treat it as unconfirmed.
- No measured RTT figures from Jakarta, Manila or Ho Chi Minh City mobile networks to Singapore game servers. The figures above are access-network latency. A real phone ping test to a Singapore server is the right validation.
- No published data on how often JS `Math.*` results actually differ between Android Chrome (V8) and iOS Safari (JavaScriptCore).

## 2. Engines and frameworks (Unity, Godot 4, Cocos Creator, Defold, web stacks with Capacitor/TWA)

### Takeaway
For a non-programmer working with an AI coding assistant, and prioritizing phone testing on day one and cheap running costs, a **TypeScript web stack (Phaser 4 or PixiJS) shipped as a PWA first, then wrapped with Capacitor or TWA for stores** is the most practical starting point. It gives instant phone testing via a URL, the largest LLM training corpus, and one language for client, server and bot sim. The main risk is WebView or browser rendering performance on low-end Android. **Unity** is the stronger choice if the team wants Photon Quantum's turnkey deterministic netcode or native-grade performance, but iteration is heavier. **Godot 4** is a good native option, but its web export is weaker (no C#, single-threaded, Compatibility renderer only), and LLMs often emit Godot 3 code.

### Inferences
- **Phone testing speed ranking (fastest first):** web stack via a LAN/tunnel URL or a static host (seconds per iteration, works on any phone and on testers' phones with no install), then Godot or Defold native APK (minutes, one-click deploy over USB), then Unity Android build (multiple minutes per build, heavier editor). For a non-programmer, "send a link to a friend" is a large advantage in the validation phase.
- **Shared-sim advantage of TypeScript:** one deterministic sim module runs in the browser client, in a Node server (Colyseus or Nakama's TS runtime) or a Cloudflare Worker for validation, and in a headless Node bot trainer. With Unity, the C# sim could run on a .NET server, but Nakama/Colyseus would need a separate port. Photon Quantum solves this, but only inside its own ecosystem.
- **Performance risk is concentrated in rendering, not logic.** 50–100 animated 2D sprites plus particles and health bars is well within WebGL2 on mid-range Android if atlases and batching are used. Low-end devices (2–3 GB RAM, old Mali GPUs) are where web and WebView builds fall short. Plan a low-end test device early (inference; no direct benchmark found).
- **Choices that lock in later:** engine language, because the sim code is the most valuable asset, and Quantum (Unity-only, ties netcode and sim to Photon). A web-first prototype can still be ported. Prototyping in TS and then moving to Unity is a rewrite, not a port.

### Gaps
- No rigorous 2025–2026 benchmark comparing Phaser/PixiJS-in-WebView vs Godot vs Unity on low-end Android with 100 animated units.
- Licensing for Godot (MIT), Phaser (MIT), PixiJS (MIT) and Defold (the Defold License, Apache-2.0 based) is from background knowledge and was not re-verified this session. Cocos Creator's license terms are conflicting across sources.
- iOS: no data on WKWebView / Capacitor performance or App Store acceptance of web-wrapped games for this genre (Apple's guideline 4.2 "minimum functionality" risk for thin wrappers is background knowledge and unverified).

## 3. Backend / multiplayer services (Colyseus, Nakama, Photon, PlayFab, UGS, Edgegap, Hathora, Cloudflare DO, Supabase Realtime)

### Takeaway
At small scale the cheapest viable options are **Colyseus (MIT, self-host, or Colyseus Cloud from $15/mo)**, **Cloudflare Durable Objects (one object per match, usage-billed, new `apac-se` hint covering Singapore)** and **Photon Quantum/Fusion (Free 100 CCU, Singapore region `asia`)**. Nakama is strong but its managed cloud is quote-based or expensive. 2026 was a year of platform deaths: Hathora game hosting shut down (May 2026), Unity Multiplay was deprecated (April 2026), and PlayFab reportedly cut its free tier. So **avoid locking game logic into a proprietary hosting API**, and prefer open-source servers that run anywhere.

### Cited Findings
**Colyseus**
- MIT-licensed Node.js framework, free for commercial use. Authoritative rooms with binary delta state sync. — [Colyseus framework](https://www.colyseus.io/framework); [bestofjs: Colyseus](https://bestofjs.org/projects/colyseus)
- Colyseus Cloud "starting at $15/mo", subscription billing with upfront provisioning and proration, and a low-performance tier meant for development. One comparison site claims 32 global locations and no CCU limits. The region list (Singapore?) was not confirmed. — [Colyseus Cloud docs: Pricing & billing](https://docs.colyseus.io/cloud/pricing-billing); [Colyseus Cloud docs: Compute plans](https://docs.colyseus.io/cloud/compute-plans); [comparegamebackends: Colyseus](https://comparegamebackends.netlify.app/backends/colyseus)

**Nakama (Heroic Labs)**
- Authoritative multiplayer via match handlers (TypeScript, Go or Lua runtime). `matchInit` returns state, a `tickRate` and a label. The tick rate must be 1–60 (Go and Lua docs). Incoming messages are buffered and passed to the loop each tick. No automatic state broadcast. — [Nakama docs: Authoritative multiplayer](https://heroiclabs.com/docs/nakama/concepts/multiplayer/authoritative/); [Nakama TS match handler reference](https://heroiclabs.com/docs/nakama/server-framework/typescript-runtime/function-reference/match-handler); [Go match handler](https://heroiclabs.com/docs/nakama/server-framework/go-runtime/function-reference/match-handler)
- Also includes accounts, leaderboards, matchmaker and storage. Open source, free to self-host. Enterprise clustering needs a commercial license. Heroic Cloud pricing is CPU-based and quote-driven. Third-party sites cite "from $600/month" (conflicting descriptions). — [Supercraft: Nakama self-hosted vs Heroic Cloud (2026)](https://crux.supercraft.host/blog/nakama-open-source-vs-managed-backend/); [toolradar: Nakama pricing](https://toolradar.com/tools/nakama/pricing); [Heroic Cloud](https://heroiclabs.com/heroic-cloud)

**Photon (Quantum / Fusion)**
- Quantum is a deterministic engine that Photon pitches for "MOBAs, RTS, brawlers…" and is free for development. It powers Stumble Guys. — [Photon blog: Quantum free for development](https://blog.photonengine.com/?p=5311); [Photon Quantum](https://www.photonengine.com:443/quantum)
- Pricing is per CCU, with about 3 GB of traffic bundled per CCU. A 1-year commitment on the 500/1,000/2,000 CCU tiers gives 2 months free. Above 2,000 CCU, titles move to Premium Cloud at $0.50/CCU for Fusion/Quantum (marketing blog figure). — [Photon blog: Multiplayer pricing made simple](https://blog.photonengine.com/multiplayer-pricing-made-simple/)
- "Free100" plans exist for Quantum and Fusion and can be combined with 100 CCU Asset Store coupons (Quantum Plus/Fusion Plus). — [Photon Fusion 2 FAQ](https://doc.photonengine.com/fusion/v2/troubleshooting/faq)
- Singapore is a Photon Cloud region (token `asia`). All regions are available to all apps at no extra charge. Clients fetch the region list from Name Servers. — [Photon Fusion regions](https://doc.photonengine.com/fusion/current/reference/regions); [Quantum 3 regions](https://doc.photonengine.com/quantum/current/reference/regions-quantum3)

**Cloudflare Durable Objects**

- **Lesson from 2026:** Hathora and Multiplay closed with weeks of notice. Keep the match server a plain process or container (Node/Colyseus, or a DO with the sim as a library) that can move between hosts in a day.

## 4. Bots / AI opponents

### Takeaway
Shipped card-deployment games almost certainly use scripted or heuristic bots (Supercell has never confirmed ladder bots, but reported changes to "tutorial bots" below 4,000 trophies and Brawl Stars' bot replacement for disconnected players show bots are part of their toolkit). Academic and hobby work shows MCTS with determinization and RL can play Clash Royale, but needs a fast headless deterministic simulator. For a tiny team: **build a rule-based or utility-AI bot first (PvE-first validates fun), use it to fill matchmaking at low player counts, and keep the sim headless so MCTS or self-play can be added later.**

### Cited Findings
- Supercell has not publicly confirmed bots in Clash Royale ladder matchmaking. — [esports.net: Does Clash Royale have bots](https://www.esports.net/news/mobile-games/does-clash-royale-have-bots/); [CyberPost](https://cyberpost.co/are-there-bots-playing-clash-royale/)
- A secondhand report (Dot Esports) says Supercell "reduced the number of tutorial bots below 4,000 trophies" after a maintenance update, and that bots appear only in matches below a 4,000-trophy average. It is undated and I could not confirm it against a Supercell post. — [Dot Esports](https://dotesports.com/?p=373692)
- Official: in Brawl Stars, a disconnected player is replaced by a bot. — [Supercell Support](https://support.clashroyale.com/hc/pl/articles/49484886660251-Unstable-Connection)
- MCTS approach (Aalto University, Boney et al., ~2021): Monte Carlo tree search with determinization for hidden information, a variant (FDTS) for large action spaces, and a "follower" policy that imitates an oracle planner from partial observations. Reportedly it needs only a few hundred battles of training. — [Aalto: Learning to Play Imperfect Information Games by Imitating an Oracle Planner](https://acris.aalto.fi/ws/portalfiles/portal/94733653/Learning_to_Play_Imperfect_Information_Games_by_Imitating_an_Oracle_Planner.pdf)
- Offline RL agent (arXiv 2504.04783, April 2025): plays real Clash Royale from screen pixels and beats the built-in AI. It is not human-level and works only with fixed decks. — [arXiv 2504.04783](https://arxiv.org/abs/2504.04783); [katacr code](https://github.com/wty-yy/katacr)
- Hobby projects: PPO with the card-placement action split to shrink the action space; simple Q-learning on nearest-enemy, distance and elixir state; deterministic C++ sim with recurrent PPO plus lookahead search. — [Real-Time-Strategy-RL-Clash-Royale](https://github.com/Jaso1024/Real-Time-Strategy-RL-Clash-Royale); [RoyalGhost Q-learning experiment](https://sam-ellgass.notion.site/Royal-Ghost-In-the-Machine-92e18d44bded4fb58ec9c382a9ea6ddd); [clash-royale-env](https://github.com/cole-zoom/clash-royale-env)

### Inferences
- **Practical bot ladder for a tiny team:**
  1. *Scripted / rule-based (days):* elixir threshold, "defend the most-threatened lane", counter-table (air vs anti-air, swarm vs splash), "push the lane where the enemy just spent". Readable rules that an AI assistant can write and a product owner can tune in a JSON/spreadsheet.
  2. *Utility AI (1–2 weeks):* score every (card, lane, position) option by weighted considerations (threat, elixir advantage, tower HP, counter value) and pick the best, with noise for difficulty levels. This is the industry-standard sweet spot for "feels human" bots.
  3. *Shallow lookahead / MCTS (later):* because the sim is deterministic and headless, you can roll out 2–5 seconds ahead for each candidate play. This is feasible on a server, or on-device with a small budget.
  4. *RL / self-play (only after launch, if ever):* expensive, and needs millions of fast headless sims. Useful offline for balance testing (bot-vs-bot win rates per card) more than as a live opponent.
- **Bots for liquidity:** at low concurrency, matchmaking against a "ghost" bot after X seconds keeps waits short. Ethics and store policy: disclose or limit it to low ranks (the CR precedent is low-trophy only). The bot can run server-side and inject commands through the same command channel, so the client cannot tell the difference and no separate netcode is needed.
- **PvE-first** (bot battles, then a campaign of hand-built AI decks) lets the team validate fun with zero backend and no player-count dependence. It reuses 100% of the sim.

### Gaps
- No public postmortem from a commercial card-deployment game (Clash Royale, Rush Royale, Clash Mini, Warcraft Rumble) detailing its AI-opponent architecture was found.
- Warcraft Rumble (Blizzard), a lane-based card-deployment game with PvE-first design, would be a relevant precedent, but its tech was not researched in this pass.

## 5. Simulation design (ECS, lane pathing, targeting, performance budget)

### Takeaway
For a 3-lane map, **lane waypoints plus simple local steering/separation** is far cheaper and more deterministic-friendly than navmesh or flow fields. Flow fields pay off only with many units sharing goals over open terrain. A data-oriented ECS (or just struct-of-arrays with a stable entity order) keeps 50–100 units trivially cheap on the CPU. **Rendering is the real budget.**

### Cited Findings
- Flow fields cost "per goal, not per agent": a thousand units sharing a goal share one field. They are good for many units with a single goal and for maze maps, but have a fixed setup cost and can be slower than standard pathfinding for simple maps with few units. They also have local-optimum issues. — [CrowdToolkit: Navigation concepts](https://jbernardic.github.io/CrowdToolkit/concepts/01-navigation/); [vonwolfehaus/flow-field](https://github.com/vonwolfehaus/flow-field); [UE5 crowd pathfinder](https://gitee.com/eloncode/ue5_crowd_pathfinder)
- Re-pathing 2,000 entities with A* every half-second caused frame spikes. The advice was to group units, path once per group, and stagger requests across frames. — [Aron Granberg forum: Moving hundreds of units effectively](https://forum.arongranberg.com/t/moving-hundreds-of-units-effectively/459)
- An RTS devlog on why pathfinding plus unit collision is hard in RTS, and a rollback-in-RTS devlog from the same project. — [Neon Marble Rust devlog: Pathfinding in RTS](https://veterannewb.itch.io/neon-marble-rust/devlog/692942/pathfinding-in-rts-why-its-a-challenge); [Rollback in RTS](https://veterannewb.itch.io/neon-marble-rust/devlog/764800/rollback-in-rts)
- Classic reference on coordinated group movement (formations, avoidance) in RTS. — [Game Developer: Coordinated unit movement](https://gamedeveloper.com/programming/coordinated-unit-movement)
- bitECS is a TypedArray-based, data-oriented JS ECS. Benchmarks exist only for desktop/Node (for example, about 335K ops/s in one noctjs scenario). One author found a JS ECS simulation 24x faster than an OOP object graph. — [bitECS (GitHub)](https://github.com/mozilla/bitecs); [DEV: Archetype ECS in TypeScript](https://dev.to/grzott/archetype-ecs-in-typescript-why-i-didnt-use-bitecs-or-miniplex-22cb); [Ankur Sethi: Data locality sometimes beats algorithmic complexity](https://ankursethi.com/blog/data-locality-sometimes-beats-algorithmic-complexity/)
- Phaser's own tutorial says standard sprite rendering handles "tens of thousands of sprites with good performance". The per-frame CPU upload is the main WebGL sprite bottleneck. — [Phaser 4 rendering concepts](https://phaser.io/tutorials/phaser-4-rendering-concepts)
- Nakama's server-side tick rate is configurable from 1 to 60 Hz. Heavy per-tick processing with many players triggers "match handler data processing too slow, dropping data". — [Nakama Go match handler](https://heroiclabs.com/docs/nakama/server-framework/go-runtime/function-reference/match-handler); [Heroic forum: Scaling authoritative matches](https://forum.heroiclabs.com/t/scaling-authoritative-matches-for-200-players-with-high-tick-rate-best-practices-and-configuration-tips/5804)

### Inferences
- **Recommended sim model:** a fixed 10–20 Hz logic tick, with rendering interpolated at 60 fps between ticks. Each lane is a polyline of waypoints, and the base, jungle or river can be extra waypoint graphs. Units hold `laneId` and `waypointIndex`, move toward the next waypoint, and switch to "chase target" when an enemy is inside aggro range. They return to the lane path after combat via the nearest waypoint.
- **Avoidance:** use cheap separation (a push-apart within a radius via a spatial hash or uniform grid), not full navmesh or RVO. Units only need to look good, and simpler rules are easier to keep deterministic.
- **Targeting rules à la CR:** a fixed priority per unit type (buildings-only, ground-only, air-capable). Retarget only when the current target dies or leaves range, which avoids flicker and saves CPU. Ties are broken by a deterministic key (distance squared, then entity ID).
- **Budget:** 100 units x 20 Hz x (spatial-hash query + move + attack) is roughly tens of thousands of simple integer operations per tick, negligible even in JS on a low-end phone. The budget goes to draw calls, overdraw from particles and spell effects, skeletal or frame animation, and per-unit UI (health bars). Use a single texture atlas, pooled objects, health bars drawn as batched quads, and cap particle counts.
- **3-lane MOBA specifics** (towers per lane, minion waves, possibly a hero unit) fit the same waypoint model. Auto-spawning minion waves are just server-tick-scheduled "commands" in the deterministic log.

### Gaps
- No mobile-device benchmark (frame time vs unit count) found for Phaser 4, PixiJS 8, Godot 4 or Unity 2D with about 100 animated units.
- No source on how Clash Royale implements unit avoidance or bridge pathing (the community sims above might reveal it but were not inspected in detail).

## 6. Anti-cheat basics and replay systems

### Takeaway
With a deterministic sim and server-stamped commands, **anti-cheat and replays come almost for free**. The server validates every command (has the card in hand, enough elixir, legal placement zone, correct tick) and can re-simulate the match from the seed plus the command log to verify the result. The replay file is just "seed + version + command list". Limits: this does not stop bots or auto-players that send legitimate inputs, and lockstep clients hold the full game state.

### Cited Findings
- Server-side replay validation: re-run the submitted inputs through the authoritative deterministic sim and reject mismatches. It requires a fixed timestep, an ordered input log and a seed, so that a divergence indicates tampering rather than engine noise. — [Bugnet: How to add server-side replay validation](https://bugnet.io/blog/how-to-add-server-side-replay-validation); [Bugnet: Replay verification failing from nondeterminism](https://bugnet.io/blog/how-to-fix-replay-verification-failing-from-nondeterministic-simulation)
- *Realms of Ruin* (RTS, GDC 2024) lists anti-cheat (detecting local modification, command validation), network sync and replays as the three reasons for a deterministic sim: "commands (inputs) generate state". — [GDC 2024 slides: Cross-Platform Determinism](https://media.gdcvault.com/gdc2024/Slides/GDC+slide+presentations/Pollard_Bradley_CrossPlatformDeterminism+2024-03-26+09.34.19.pdf)
- Server-authoritative logic is the standard way to prevent state tampering. Scripts sending valid inputs at superhuman speed look like legitimate inputs to the server. — [AccelByte: Server authoritative logic to prevent cheating](https://accelbyte.io/blog/server-authoritative-logic-to-prevent-cheating); [HackerNoon: Building a tamper-proof 60fps real-time arcade engine](https://hackernoon.com/building-a-tamper-proof-60-fps-real-time-arcade-engine)
- A rollback library offers a validation playback mode that checks per-frame checksums recorded during the original match. — [fortress-rollback: Replay](https://wallstop.github.io/fortress-rollback/replay/)
- Supercell's account flow issues signed tokens from an account API, which the client presents to the game server. — [ScyllaDB tech talk: Supercell](https://www.scylladb.com/tech-talk/real-time-persisted-events-at-supercell/)

### Inferences
- **Minimum viable anti-cheat for this game:** (1) the server owns elixir, hand and deck cycle (the client only requests "play hand slot 2 at x,y"); (2) the server validates placement zone, elixir and cooldown, then stamps the execution tick; (3) the server decides the match result, either by running the sim itself or by re-simulating the command log after the match; (4) clients exchange periodic state checksums to detect desyncs and modified clients.
- **Hidden information:** with command relay, the client needs only the opponent's commands as they are played, so the opponent's hand and next card need never be sent. Keep deck shuffling seeded on the server and reveal cards only when played. This avoids the "maphack" problem of pure peer lockstep.
- **Replays:** store `{simVersion, seed, decks, commands[]}`, a few KB per match. Replays break when the sim changes, so keep old sim versions or record periodic snapshots if replays must survive balance patches.
- **Server re-sim cost:** about 100 units for 3–6 minutes at 20 Hz is 3,600–7,200 ticks, which runs in well under a second headless. So post-match verification is cheap even on a $5 VPS or in a Worker (inference; not benchmarked).

### Gaps
- No card-game-specific public write-up on this exact validation setup was found. Supercell has not documented its anti-cheat.

## 7. Staged roadmap for a tiny team, and which choices are hard to reverse

### Takeaway
Validate fun first with a **single-player, bot-opponent web prototype playable from a phone URL (weeks 1–4)**. Then add **2-player command-relay multiplayer on a Singapore server (weeks 4–8)**. Then a **closed SEA playtest with bots filling queues (months 2–4)**, then store wrappers, accounts and meta-progression (months 4–9). The hardest choices to reverse are: (a) whether the sim is deterministic integer/fixed-point from day one, (b) which language the sim is written in, since that decides whether server and bots can reuse it, and (c) coupling to a proprietary netcode or host (Quantum, Multiplay-style hosting), as 2026's shutdowns showed.

### Cited Findings
(This section synthesizes the findings above. Supporting citations:)
- Platform-risk precedents: Hathora game hosting ended May 5, 2026 after an AI pivot. Stormgate lost multiplayer as a result. Unity Multiplay was deprecated April 1, 2026. — [TechSpot](https://www.techspot.com/news/111969-stormgate-servers-go-dark-following-ai-focused-hosting.html); [Unity status notice](https://status.unity.com/info_notices/362941)
- Retrofitting determinism is costly. Practitioners recommend fixed-point from the start and banning floats from the sim. — [GDC 2024 slides](https://media.gdcvault.com/gdc2024/Slides/GDC+slide+presentations/Pollard_Bradley_CrossPlatformDeterminism+2024-03-26+09.34.19.pdf); [Game Developer: Minimizing the pain of lockstep multiplayer](https://gamedeveloper.com/programming/minimizing-the-pain-of-lockstep-multiplayer)
- Photon offers free development access and a Free100 CCU plan for Quantum. Colyseus is MIT. Colyseus Cloud starts at $15/mo. Cloudflare DO bills per use. — [Photon blog](https://blog.photonengine.com/?p=5311); [Colyseus Cloud docs](https://docs.colyseus.io/cloud/pricing-billing); [Cloudflare DO pricing](https://developers.cloudflare.com/durable-objects/platform/pricing)
- LLM-assisted development works better in TS/web or C# than in GDScript (Godot 3 vs 4 API confusion), and struggles with large, tightly timed real-time codebases unless broken into small modules. — [Medium: AI coding tools for game dev](https://chierhu.medium.com/ai-coding-tools-for-video-game-development-a-first-principles-analysis-of-what-actually-works-90dfa10edd13); [Godot forum vibe-coding postmortem](https://forum.godotengine.org/t/post-mortem-of-my-failed-attempt-to-vibe-code-a-metroidvania-game/137567/1)

### Inferences
**Recommended default path ("Path A: TypeScript all the way")**
- *Stack:* TypeScript, with Phaser 4 or PixiJS for rendering. A pure-TS deterministic sim package (integer/fixed-point, seeded PRNG, fixed 10–20 Hz tick) with no rendering imports. Vite dev server for hot reload. Colyseus (Singapore VPS or Colyseus Cloud) or a Cloudflare Durable Object (`apac-se`) as match server. Supabase or Nakama later for accounts and meta-game. PWA for testers, then Capacitor (or TWA on Android) for stores.
- *Weeks 1–2:* the sim plus a debug renderer. One lane, then three lanes; 6–8 cards; elixir; towers; win condition. Playable vs a scripted bot on a phone through a URL. Unit tests that run the same seed and commands twice and assert identical state hashes. Make that test pass from day one.
- *Weeks 3–4:* utility-AI bot, 12–20 cards, basic art, 3–6 minute match tuning, PvE playtests with 5–20 people via link. Measure fps on the cheapest Android device available.
- *Weeks 4–8:* 2-player online. Server-stamped commands with about 200 ms delay; reconnection by replaying the command log; server-side validation; checksums; replays. Deploy the room server to Singapore. Test over real 4G in ID/PH/VN.
- *Months 2–4:* closed online playtest. Matchmaking with bot fill after N seconds, basic accounts (Supabase Auth or Nakama), telemetry (card win rates from server logs), and balance via data files.
- *Months 4–9:* store wrapping (Capacitor/TWA), progression and economy, IAP, anti-cheat hardening, soft launch in one or two SEA countries. Port the renderer to native (Godot/Unity) only if WebView performance on target devices proves inadequate. The TS sim can stay as the server/validator, but a native client would need the sim re-implemented or embedded (for example, a JS runtime), which is the main cost of this path.

**Alternative ("Path B: Unity + Photon Quantum")**
- Choose this if the team values native performance and turnkey deterministic netcode (rollback, reconnection, replays, Singapore region, Free100 CCU) over iteration speed and portability. Cost: Unity Personal is free under $200k. Quantum is free in development, then priced per CCU. Downsides: slower phone iteration (APK builds), C# and Unity editor complexity for a non-programmer, and the sim, netcode and hosting all tied to Photon.

**Alternative ("Path C: Godot 4 native + Colyseus/Nakama")**
- Good native performance, small engine, MIT. But a GDScript sim cannot run on a Node server without a rewrite, the web export is a weaker phone-testing route, and LLMs often produce Godot 3 code. Server-authoritative state-sync (server runs a TS or Go sim, Godot renders) is possible, at the cost of duplicated logic.

**Hard to reverse (decide in week 1):** deterministic fixed-point sim, sim language and module boundary (sim has no engine imports), command-relay protocol shape, server-side ownership of deck and elixir. **Easy to change later:** renderer/engine for presentation, backend host (if the server is a plain container/process), accounts provider, art pipeline, bot sophistication.

### Gaps
- No published timelines from comparable tiny-team card-deployment or lane games were found to calibrate the weeks-vs-months estimates. They are reasoned estimates, not sourced.
- No data on Google Play or App Store review outcomes for Capacitor/TWA-wrapped real-time PvP games specifically.
- iOS-specific constraints (WKWebView performance, App Store guideline 4.2 for web wrappers, background WebSocket handling) were not researched in this pass.
